# 초보자 검증 체크포인트

각 단계는 말하기, 코드 수정, 재실행으로 증명합니다. 단순히 읽었다고 체크하지 마세요.

## 1단계: 빌드 증명

- CMake 구성과 빌드가 경고 없이 끝난다.
- CTest 2개가 모두 통과한다.
- `expected_demo`에서 성공 1회, 실패 2회, 이동 1회를 확인한다.

통과 기준: 명령과 출력 결과를 스스로 다시 재현할 수 있다.

## 2단계: 타입 계약 설명

다음 질문에 한 문장씩 답합니다.

1. `std::expected<int, DivideError>`가 동시에 보관하는 활성 값은 몇 개인가?
2. `if (result)`를 먼저 실행하는 이유는 무엇인가?
3. 오류 코드 `-1`보다 별도 오류 타입이 나은 점은 무엇인가?

통과 기준: “성공 또는 실패 하나”, “안전한 활성 값 접근”, “계약과 오류 정보의 명시성”을 포함한다.

## 3단계: 값 범주와 수명 증명

`main.cpp`에서 아래 식을 찾아 옆에 직접 분류를 적어 봅니다.

- `parsed`: lvalue
- `Quantity{number}`: prvalue
- `std::move(movable).value()`: xvalue
- `*parsed`: 결과 객체 내부를 가리키는 lvalue

통과 기준: `quantity` 참조가 `parsed`보다 오래 살아서는 안 되는 이유와 이동 후 `movable`의 값을 기대하면 안 되는 이유를 설명한다.

## 4단계: 코드 변경 증명

`problem.cpp`에 `safe_divide(-9, 3)`을 호출하여 결과가 `-3`인지 검사합니다. 이어서 오류 문구를 바꾸고 출력도 바뀌는지 확인합니다.

통과 기준: 변경 후에도 CTest 2개가 통과한다.

## 5단계: 아키텍처와 실행 관점

- 입력 검증, 도메인 타입, 응용 서비스, 출력의 역할을 각각 말한다.
- 성공 여부 검사가 기계 수준에서 로드·비교·조건 분기가 될 수 있음을 설명한다.
- 정확한 명령은 CPU·ABI·컴파일러·최적화 옵션에 따라 달라진다고 덧붙인다.

통과 기준: 역할 분리가 변경 범위를 줄이는 예를 하나 든다. 예: 공백 허용 정책은 출력 계층이 아니라 파서에서 바꾼다.
